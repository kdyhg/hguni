# 운영 안내

## 매일 시작 전

- 설정의 준비 상태 5개가 모두 준비됨인지 확인한다.
- 중계 heartbeat와 SQL health가 30초 이내인지 확인한다.
- 카탈로그가 24시간 이내이며 담당교사·허용 벌점이 원본에 존재하는지 확인한다.
- 학생회에는 당일 PIN만 교사가 직접 입력한다.

## 상태별 대응

| 표시 | 의미 | 조치 |
|---|---|---|
| 전송 중 | queued/executing | 같은 건을 새 UUID로 다시 누르지 않는다. |
| 반영 완료 | SQL 영수증과 원본 key 확인 | 다음 학생을 입력한다. |
| 반영되지 않음 | 원본 쓰기 없음이 안전하게 확인됨 | 교사가 원인을 확인한 뒤 기존 요청을 재처리한다. |
| 확인 필요 | 커밋 여부 불명 | `HguniReceipt`를 먼저 조회한다. 임의 재입력 금지. |
| 취소 승인 대기 | 학생회 요청만 접수 | 교사가 대상·교사·항목·시간을 검토한다. |
| 교사 직접 처리 필요 | 자동 DELETE 미검증/권한 없음 | 원본에서 처리 후 중계가 원본 상태를 다시 확인한다. |

## 장애와 복구

- 인터넷 단절: 브라우저 입력을 로컬에 쌓지 않는다. 복구 뒤 새로 검색한다.
- SQL timeout/연결 유실: uncertain으로 두고 영수증을 조회한다.
- report 유실: 중계가 같은 request ID 영수증을 읽어 reconcile한다.
- 활동 종료/긴급 중지: 신규 접수와 미실행 job을 차단한다. 이미 authorize된 건은 결과를 확인한다.
- rollback: 신규 접수 중지 → 진행 건 복구 → 호환되는 앱/중계 버전 복원 → migration 호환 확인. 원본 벌점 일괄 삭제를 rollback으로 사용하지 않는다.

기술 로그 기본 보관은 30일을 제안한다. 감사/부과/학생 snapshot의 실제 보관기간은 학교 개인정보 방침을 확인해 정한다.
